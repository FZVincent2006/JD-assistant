# 中国区 Outlook Recruiting 邮箱飞书提醒设计

日期：2026-07-17
状态：用户已确认
目标项目：招聘 JD 发布助手

## 1. 目标

在现有 Chrome/Edge 招聘助手扩展中新增一个本机邮件监控能力：

- 监控 Chrome 中已登录的中国区 Outlook 邮箱 `recruiting@zhenfund.com`。
- 邮箱入口为 `https://partner.outlook.cn/mail/`。
- 招聘平台发送的邮件不提醒。
- 个人直接投递、自荐及其他未命中招聘平台规则的邮件全部提醒。
- 提醒只发送到一个专用私密飞书群。群中有用户及另外三位同事，共四位接收人；机器人只加入该群。
- 四位接收人收到提醒后自行打开 Outlook 处理邮件。

该能力只需在用户的 Mac 开机、Chrome 运行且 Outlook 标签页保持登录时工作。Mac 休眠或关机期间允许暂停，恢复后执行补扫。

## 2. 首期边界

首期只做“发现新邮件并提醒”：

- 不自动回复邮件。
- 不自动下载、解析或转发简历附件。
- 不进行候选人评价或岗位匹配。
- 不改变邮件已读状态，不移动、分类或删除邮件。
- 不把邮件正文或附件发送到飞书。
- 不部署云服务器，不接入全球版 Outlook Connector，也不依赖 Microsoft Graph。

未来如果需要自动回复、简历解析或候选人分流，应在本监控稳定后单独设计。

## 3. 已验证环境

2026-07-17 已在用户当前 Chrome 会话中只读验证：

- 页面标题为 `邮件 - Recruiting - Outlook`。
- 当前邮箱为 `recruiting@zhenfund.com`。
- 邮箱运行在 `partner.outlook.cn` 中国区环境。
- 邮件列表中的邮件行使用 `role="option"`。
- 邮件行具有稳定的 `data-convid` 会话标识和 `data-focusable-row` 标识。
- 邮件行的可访问性元数据包含发件人、主题、时间、附件状态及正文预览。

实现不得保存或发送完整的可访问性标签。提取器优先读取结构化的可见子元素；只有缺少结构化字段时才把可访问性标签作为回退输入，并在内存中立即裁剪为允许的提醒字段。

## 4. 推荐架构

首期采用零服务器架构：

```text
partner.outlook.cn 邮件列表
        ↓
Outlook Monitor content script
        ↓
扩展后台 service worker
        ↓
专用四人飞书群的自建机器人 Webhook
```

默认浏览器可以继续使用 Edge。监控只依赖 Chrome 中实际打开的 Outlook 标签页。

### 4.1 Outlook Monitor content script

新增独立 content script，只匹配：

```text
https://partner.outlook.cn/mail/*
```

职责：

- 检查当前页面是否为已登录的 Outlook 邮箱。
- 读取邮件列表中已渲染的邮件行。
- 提取最小元数据。
- 监听邮件列表 DOM 变化。
- 接收后台发出的定时扫描请求。
- 在需要补扫时遍历 Outlook 的虚拟列表，但不点击邮件。

该模块与现有 Boss 直聘、脉脉和飞书文档 content script 分开，不复用页面选择器。

### 4.2 扩展后台

后台负责：

- 使用 `chrome.alarms` 每 10 分钟发起一次扫描。
- 接收页面变化触发的轻量扫描结果。
- 建立首次启用基线。
- 生成去重键并保存最近 90 天的记录。
- 应用招聘平台排除规则。
- 管理飞书待发送队列、重试和发送状态。
- 检测 Outlook 标签页关闭、登录失效和监控恢复。

### 4.3 飞书群自建机器人

扩展后台直接调用专用私密群的机器人 Webhook：

- 不增加 macOS 本地助手。
- 不申请飞书企业通讯录权限。
- 不申请向其他群或公司全员发送消息的能力。
- Webhook 只绑定用户指定的四人私密群。
- 启用飞书机器人签名校验。

Webhook 地址与签名密钥保存在 `chrome.storage.local`，不得进入源码、测试夹具、构建产物日志或同步存储。

## 5. 邮件扫描与补扫

### 5.1 正常扫描

触发来源：

1. 页面载入并确认登录后扫描一次。
2. 邮件列表变化后，等待 3 秒稳定期再扫描。
3. 后台每 10 分钟主动扫描一次。
4. Chrome 或 Mac 恢复运行后扫描一次。

扫描只读取列表，不点击邮件，因此不会标记已读。

### 5.2 首次基线

首次成功启用监控时：

- 读取当前列表和必要的补扫范围。
- 把当前存在的邮件写入去重存储。
- 不发送历史邮件提醒。
- 记录基线完成时间和最新邮件边界。

用户可以在设置中执行“重新建立基线”。该操作必须二次确认，因为它会让当前邮件重新成为历史基线。

### 5.3 虚拟列表补扫

Outlook 只在 DOM 中保留可见行及少量缓冲行。为避免 Mac 休眠后只读取到最上面的少数邮件，监控使用边界追踪：

- 保存上次扫描已知的最新边界和最近去重键。
- 如果本次顶部列表无法与已知边界衔接，在 Outlook 标签页处于后台时向下遍历虚拟列表。
- 每次遍历读取一批邮件标识和时间，直到找到已知边界。
- 找到边界后恢复原滚动位置。
- 单次最多检查 100 封或最近 30 天，以先到者为准。
- 如果仍找不到边界，暂停自动提醒并显示“需要人工检查监控缺口”，不把无法确认的新旧邮件静默标记为已处理。

补扫不得打开邮件、改变选择项或修改已读状态。

## 6. 提取字段与去重

允许提取和发送的字段只有：

- 发件人显示名称；
- 发件人邮箱；
- 邮件主题；
- 收件时间；
- 是否包含附件；
- Outlook 收件箱入口。

不允许保存或发送：

- 邮件正文或正文预览；
- 附件名称、附件内容；
- 邮件中的电话号码、学校、候选人经历等正文信息；
- 完整 DOM 或完整 `aria-label`。

每次提醒使用以下去重键：

```text
SHA-256(data-convid + normalized-received-time)
```

这样同一会话收到新回复时可以再次提醒，而页面刷新、扩展重启和重复扫描不会再次提醒同一版本。

去重记录保留 90 天。保存内容仅包括哈希键、收件时间、过滤结果和发送状态。

## 7. 招聘平台排除规则

因为该邮箱只处理招聘，首期不使用 AI 判断邮件语义：

- 命中招聘平台规则：记录为平台邮件，不提醒。
- 未命中规则：视为个人投递或自荐，发送提醒。

规则支持：

- 发件人完整邮箱；
- 发件人域名；
- 发件人显示名称；
- 主题固定前缀或关键词。

规则采用大小写不敏感的精确值或简单包含匹配，不允许用户直接输入任意正则表达式。

实现不猜测真实平台域名。正式启用前，用户通过设置页录入当前使用的招聘平台及其真实发件邮箱或域名。设置页提供“检查规则”功能，用最近已扫描邮件的最小元数据展示哪些规则会命中，但不发送提醒。

安全策略是宁可多提醒，不静默漏掉个人投递。规则变更只影响后续扫描，不追溯撤销已经发送的提醒。

## 8. 飞书提醒

### 8.1 单封提醒

正常情况下，每封非平台新邮件发送一张飞书消息卡片：

```text
收到新的非平台简历投递

发件人：<显示名称> <邮箱>
主题：<邮件主题>
时间：<北京时间>
附件：有 / 无

[打开 Recruiting 邮箱]
```

按钮打开：

```text
https://partner.outlook.cn/mail/inbox
```

不生成无法验证稳定性的单封邮件深链。

### 8.2 批量补发

Mac 唤醒或监控恢复后，如果一次发现 5 封及以下新邮件，逐封提醒；超过 5 封时发送一张汇总卡片，列出全部邮件的允许字段。

汇总中的每封邮件仍单独写入去重记录和发送状态。

### 8.3 发送可靠性

- 只有飞书返回成功后才把邮件标记为已提醒。
- 失败记录进入本地待发送队列。
- 重试间隔为 1 分钟、5 分钟、15 分钟，之后每 30 分钟一次。
- 同一提醒最多保留 24 小时；超过 24 小时仍失败时显示人工处理提示。
- 扩展重启后恢复待发送队列。

## 9. 监控状态与异常

监控状态包括：

- 未配置；
- 正在建立基线；
- 正常监控；
- Outlook 标签页缺失；
- Outlook 登录失效；
- 正在补扫；
- 监控缺口待检查；
- 飞书机器人不可用；
- 已暂停。

异常通知：

- Outlook 标签页关闭或登录失效持续 30 分钟后，在专用飞书群发送一次“邮箱监控已暂停”。
- 恢复正常后发送一次“邮箱监控已恢复”。
- 飞书本身不可用时，使用 Chrome 本地通知和扩展徽标提示，不尝试通过其他渠道发送。
- 同一故障状态不重复刷屏。

监控暂停期间不丢弃去重边界；恢复后先补扫，再恢复正常扫描。

## 10. 扩展界面

在现有侧边栏中新增独立的“Outlook 简历提醒”入口，避免改变 Boss、脉脉和飞书文档模式。

界面包含：

- 开启/暂停监控；
- 当前目标邮箱：`recruiting@zhenfund.com`；
- Outlook 标签页与登录状态；
- 最近成功扫描时间；
- 最近成功提醒时间；
- 当前待发送数量；
- 招聘平台排除规则管理；
- 飞书机器人 Webhook 与签名配置；
- “发送测试提醒”；
- “检查规则”；
- 最近 20 条事件记录；
- “重新建立基线”。

只有以下条件全部满足时才能开启正式监控：

1. 找到已登录的 `recruiting@zhenfund.com` Outlook 页面。
2. 已配置飞书机器人 Webhook 和签名。
3. 测试提醒发送成功。
4. 用户确认平台排除规则。
5. 首次基线建立成功。

## 11. 安全与隐私

- 机器人只存在于用户和三位同事组成的专用私密群。
- 不向公司全员、其他群或外部服务发送消息。
- 不请求飞书通讯录权限。
- 不读取或保存附件。
- 不持久化邮件正文或正文预览。
- 扩展日志不得包含候选人邮箱、主题、正文、附件或 Webhook 密钥。
- 设置页显示 Webhook 时默认遮盖，只允许替换，不提供复制明文按钮。
- 导出诊断信息时只包含状态、时间、错误码和哈希后的邮件键。
- 如果 Webhook 泄露，用户应在飞书群机器人设置中重置并在扩展中替换。

## 12. 测试与验收

### 12.1 自动化测试

- Outlook 行解析：结构化字段、回退解析、字段缺失和页面改版保护。
- 隐私保护：原始正文预览与完整可访问性标签不会进入输出、存储或日志。
- 基线：首次启用不提醒历史邮件。
- 去重：刷新、重启、重复扫描不重复提醒。
- 会话更新：同一 `data-convid` 的新收件时间产生新提醒。
- 平台规则：邮箱、域名、显示名称和主题规则。
- 补扫：找到边界、超过范围、恢复滚动位置和缺口状态。
- 飞书签名、消息卡片、单封提醒和批量提醒。
- 发送失败、重试、重启恢复和 24 小时失败状态。
- 标签页关闭、登录失效、暂停和恢复状态。
- 现有 Boss、脉脉、飞书文档测试全部继续通过。
- 完整 `npm test` 和 `npm run build` 必须通过。

### 12.2 人工验收

在测试飞书群和真实 `recruiting@zhenfund.com` 邮箱中完成：

1. 配置只包含四位接收人的私密群机器人。
2. 发送测试提醒并确认只有该群收到。
3. 建立当前收件箱基线，确认历史邮件没有被推送。
4. 从个人邮箱发送一封带附件测试投递，确认收到单封提醒。
5. 从已配置的平台规则来源发送或选择测试邮件，确认不提醒。
6. 刷新 Outlook、重启扩展和重启 Chrome，确认不重复提醒。
7. 临时关闭 Outlook 标签页，确认 30 分钟故障提醒和恢复提醒。
8. 模拟飞书发送失败，确认待发送队列和恢复补发。
9. 检查测试邮件仍保持原有已读状态。
10. 检查飞书消息、扩展存储和诊断日志中没有正文或附件内容。

## 13. 交付与成本

首期不需要服务器或付费第三方服务：

- 服务器费用：0。
- 软件费用：0。
- 运行成本：用户现有 Mac、Chrome 和飞书。
- 预计实现与验证工作量：2–4 个工作日。

主要维护成本来自 Outlook 网页结构变化。如果邮件行的稳定属性或可访问性结构变化，解析器应进入明确的“不兼容”状态，而不是继续发送可能错误的提醒。预计一次结构适配需要半天到一天，实际频率取决于 Outlook 页面更新。

## 14. 不可避免的限制

- Mac 关机或休眠时不实时提醒，只在恢复后补扫。
- Chrome 必须运行，Outlook 标签页必须保持登录。
- 该方案依赖 Outlook 网页结构，稳定性低于正式 Graph 或 IMAP 接口。
- 单次补扫上限为 100 封或 30 天；超过上限时必须人工检查。
- Chrome 本地配置的 Webhook 密钥可被拥有本机和浏览器配置访问权的人提取。扩大到多人或多机部署前，应改用 macOS 钥匙串、本地助手或托管密钥服务。
- 招聘平台过滤质量取决于用户维护的真实发件规则；未知平台首次出现时可能产生一次多余提醒。
